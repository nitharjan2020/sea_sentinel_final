# SEA-Sentinel

Open-data proof of concept for **early detection, nowcasting and 1–4-week probabilistic forecasting**
of priority animal diseases in Southeast Asia (WOAH International Datathon 2026).

- **Countries (11):** Brunei, Cambodia, Indonesia, Laos, Malaysia, Myanmar, Philippines, Singapore,
  Thailand, Timor-Leste, Vietnam
- **Diseases (2):** HPAI in poultry and ASF in domestic swine. Rabies in dogs was in the original
  scope but was dropped: its records are sparse and there are no dog population data.

## Reproducing the results (step by step)

Requirements: Python 3.11 or newer (developed on 3.13) and git. No external downloads are needed,
because the raw data snapshots are already in `data/raw/`.

1. **Clone and enter the repository.**
   ```bash
   git clone <repository-url> sea_sentinel && cd sea_sentinel
   ```
2. **Create the environment** (dependencies are pinned in `requirements.txt`).
   ```bash
   python -m venv .venv
   .venv/Scripts/activate            # Windows  (macOS/Linux: source .venv/bin/activate)
   pip install -r requirements.txt
   pip install -e .
   ```
3. **(Optional) Check that the raw data are intact.** Compare each file's SHA-256 with
   `data/raw/MANIFEST.csv`:
   ```bash
   python -c "import pandas as pd; from sea_sentinel.ingest import sha256; from sea_sentinel.config import RAW_DIR; m=pd.read_csv(RAW_DIR/'MANIFEST.csv'); print(all(sha256(RAW_DIR/r)==h for r,h in zip(m.raw_name,m.sha256)))"
   ```
4. **Run the pipeline** (about 5 minutes). It rebuilds every table in `data/processed/` and
   `outputs/tables/`, every figure in `outputs/figures/`, and the technical report. Edit the report's
   prose in `docs/report_template.md`; its numbers and results tables are always computed.
   ```bash
   python run_pipeline.py                  # stages 1-12: ingest ... detection, nowcasting, forecasting, alerts, report
   python run_pipeline.py --review-dedup   # also re-runs the dedup threshold review (about 2 minutes)
   ```
5. **Run the tests.**
   ```bash
   pytest                                  # unit tests
   ```

Results are deterministic: no network access is needed, and the simulation uses a fixed seed.

**Re-downloading the sources instead.** To refresh the data, re-download the sources (see
[Data sources](#data-sources)), put the files in one folder, and run
`SEA_SENTINEL_SOURCE_DIR=<folder> python run_pipeline.py --force-ingest`. Newer snapshots will
change the numbers.

**How each snapshot was downloaded** (needed only to refresh the data):
- *EMPRES-i Plus* (<https://empres-i.apps.fao.org/>), event export with these filters:
  - Disease = Influenza - Avian, African swine fever, Rabies (rabies rows are now excluded as
    outside scope)
  - Region = Asia, Subregion = South-Eastern Asia
  - Diagnosis source / status and animal type = All

  The filters are recorded in the header of the raw file.
- *WAHIS* (<https://wahis.woah.org/>): the event list, filtered to the 11 countries and the three
  diseases, exported as CSV.
- *FAOSTAT* (<https://www.fao.org/faostat/en/#data/QCL>), *Crops and livestock products* with:
  - Element = Stocks
  - Items = Chickens, Ducks, Geese, Turkeys, Swine / pigs
  - Years = 2000–2024, for the 11 countries
- *World Bank, NOAA CPC and Natural Earth*: `python -m sea_sentinel.download`, which writes the three
  files into the source folder (`--out <folder>` to choose another).

**Why WAHIS is not added to the counts.** The WAHIS exports list *events*, and one event can contain
many outbreaks. EMPRES-i already contains thousands of WOAH-sourced outbreak records (the exact
count is in [§2 of the report](docs/technical_report.md#2-data)). Adding the two would double-count,
so the WAHIS events are kept as a separate table. They are used to cross-check the countries and
diseases each source covers.

## Processing rules

1. **Scope filter.** A record is kept only if it is confirmed and falls in one of these groups:
   HPAI in domestic or unspecified birds (LPAI serotypes excluded) or ASF in domestic swine (wild
   boar excluded). Rabies is outside scope. Every excluded row keeps its reason; see
   `outputs/tables/empres_scope_filter.csv`.
2. **Dates.** The event date is the observation date. When that is missing, the report date is used
   instead and the row is flagged `date_basis = "report"`; the share per disease is in
   [§3.1 of the report](docs/technical_report.md#31-standardisation-and-scope). Reporting delays are computed only when both dates
   exist. Delays that are negative or longer than a year are flagged and left out of delay
   statistics.
3. **Deduplication** (`dedup.py`) runs in two passes:
   - *Exact repeats:* rows from one source with the same place, coordinates, date and locality are
     merged. This includes the per-species rows of one outbreak (e.g. chickens and ducks in the same
     village on the same day). Every animal type is kept in `animal_types`.
   - *Cross-source repeats:* rows from different reporting channels are merged when they are at most
     1 km apart (great-circle distance) and at most 3 days apart. Pairs are linked closest first, and
     a group never holds two rows from the same source. Nearby rows from one channel are distinct
     outbreaks; WOAH rows, for instance, carry unique outbreak IDs.

   In each merged group, the kept record is chosen in this order: national authority over WOAH over
   FAO over media, then a record with an observation date, then the earliest report.

   **How the thresholds were chosen** (`dedup_review.py`, `outputs/figures/dedup_review.png`).
   Pairs of nearby records from the *same* channel show how outbreaks normally cluster in space and
   time. Pairs from *different* channels show that clustering plus any duplicates. The ratio of
   cross-source to same-source pairs is therefore flat where there are no duplicates, and rises where
   duplicates sit. The measured ratios, the sensitivity of the outbreak count to other thresholds,
   and the record counts before and after deduplication are in
   [§3.2 of the report](docs/technical_report.md#32-deduplication).
4. **Missing is not zero.** In `weekly_panel.csv`, weeks before a series' first report or after its
   last report have `outbreaks = NaN`. Weeks in between count as reported zeros. Silent stretches of
   26 or more weeks inside that window are flagged `long_gap`.
5. **Population offsets** (`denominators.py`). Each week gets an at-risk population from FAOSTAT
   annual stocks: `population_head` and `log_population`.
   - *What is counted:* HPAI uses chickens + ducks + geese + turkeys; ASF uses pigs.
   - *No look-ahead:* FAOSTAT publishes 1–2 years late, so each annual value is pinned to 1 July two
     years after its reference year (`config.POPULATION_LAG_YEARS`), and weeks in between are
     interpolated on the log scale. Each week thus uses essentially only stocks already published.
   - *Beyond the last anchor:* weeks after July 2026 carry the 2024 value and are flagged
     `population_extrapolated`.
   - *No stock reported:* Singapore pigs ("data cannot exist") get a missing population, not zero.
   - *Data quality:* the share of official (non-estimated) FAOSTAT values per series is in
     `population_denominators.csv`; the weakest series is named in
     [§11 of the report](docs/technical_report.md#11-limitations). The national census totals in the
     GLW metadata are compared with FAOSTAT for the same year in `population_census_check.csv`
     ([§3.4](docs/technical_report.md#34-population-offsets)).
6. **Forecast eligibility.** A series is eligible for forecasting when it has at least 100
   observation-dated outbreaks, at least 104 weeks in its reporting window, and at least 30 weeks
   with outbreaks.

## Anomaly detection

`detection.py` flags weeks with unusually many reported outbreaks. It runs on the 20 series with at
least detection-level coverage.

**How each week is judged.** Week *t* is compared only with data from before week *t − 2*. Nothing
from later weeks is used, and the 2-week guard keeps an emerging outbreak out of its own baseline.
Weeks outside a series' reporting window are left out of the baseline, not counted as zeros. A week
can only alarm if at least one outbreak was reported.

**Two baselines:**

| Method | Baseline | Alarm when | Default |
|---|---|---|---|
| Rolling (EARS-C2 style) | mean and SD of the previous 52 weeks (at least 26 observed) | count > mean + z·SD | z = 3 |
| Negative binomial | GLM on the previous 104 weeks: annual seasonality + log-population offset | count > upper q-quantile of NB(μ, α) | q = 0.99 |

The negative-binomial (NB) fit is refitted once with past outbreak weeks down-weighted (Farrington
style; quasi-Poisson residual > 2.58). Its dispersion α is then estimated only from weeks that were
not flagged. Without this, earlier epidemics inflate α so much that later alarms are suppressed.

**Evaluation** (`detection_eval.py`). There is no record of weeks with truly no outbreaks, so the
methods are judged three ways. Series are weighted equally.

- *False-alert rate:* the share of weeks that alarm on real data. Some of these alarms are genuine
  surges, so this is an upper bound.
- *Simulated sensitivity (simulation):* a synthetic outbreak is added at every evaluable week in
  turn. Its size is drawn from Poisson(k × baseline SD) and spread over 3 weeks; it counts as
  detected if any of those 3 weeks alarms.
- *WAHIS events:* an official event start (new or recurrent introduction) counts as detected if an
  alarm falls within 2 weeks before to 4 weeks after it. The chance rate is what an alarm pattern
  with no real signal would score in the same window.

Two robustness checks run with the evaluation:
- *Independence from WAHIS:* WAHIS events and WOAH-sourced EMPRES-i records come from the same
  national reports, so hit rates are split by whether the event window holds a WOAH-sourced record
  (`detection_wahis_independence.csv`).
- *Population offsets:* the negative-binomial detection is re-run without the offset, to show how
  much FAOSTAT errors could move alarms (`detection_offset_sensitivity*.csv`).

**Results:** see [§6.3 of the technical report](docs/technical_report.md#63-results), generated by the pipeline
from the current data. It covers alarm rates, WAHIS events detected against chance, simulated
sensitivity, recovery after large epidemics, the best and worst series, and the current alerts.
Full threshold curves are in `detection_performance.csv` and `detection_tradeoff.png`; current
alerts are in `detection_latest_alerts.csv`.

**Real-time replay** (`detection_realtime.py`). The results above use finalized data. At every week
from January 2022 to one year before the end of the panel, each series is cut back to the records
reported by then, and both methods judge the last 12 weeks again, from the counts as reported and
from nowcast-corrected counts. This shows how many finalized-data alarms were raised in real time,
how late, and how many real-time alarms the final data confirm. Results: [§6.4 of the
report](docs/technical_report.md#64-real-time-replay); tables `detection_realtime_*.csv`.

**Subnational detection** (`detection_subnational.py`). For HPAI and ASF series with at least 5
provinces (admin1) of 20 or more outbreaks, both baselines are fitted per province, and the system
alarms when the most unusual province passes a cut-off. Per-province default thresholds would alarm
in most weeks, so the cut-off is set to give the same alarm rate as national detection. Both are
compared on WAHIS events and on simulated clusters added to one province. Results: [§6.5 of the
report](docs/technical_report.md#65-subnational-detection); tables `detection_subnational*.csv`.

## Nowcasting

For a recent week, the count reported so far is too low because some outbreaks have not been
reported yet. `nowcast.py` estimates the count that will eventually be reported within 52 weeks,
for every one of the last 52 weeks. It uses only data that had been reported by the as-of week.

1. **How much has been reported so far.** A chain-ladder reporting triangle estimates the
   completeness F(d): the share of a week's outbreaks reported within d weeks. It uses the last two
   years and corrects for the fact that recent delays are not yet fully observed. Sparse series use
   the delay pattern pooled across countries for the same disease.
2. **Filling in the rest.** The count reported so far is modelled as C ~ Poisson(λ·F(d)). The
   weekly rate λ gets an empirical-Bayes Gamma prior from the 13 most recent weeks that are at least
   half complete; its variance comes from how much those weeks vary. The outbreaks still to be
   reported then follow a negative-binomial distribution, which gives exact 80% and 95% intervals,
   even for weeks where nothing has been reported yet.
3. **Batch-reporting flag.** Some series arrive mostly in a few bulk uploads, so each outbreak
   does not have its own independent delay and the model's main assumption fails. The most
   concentrated series is named in [§7.1 of the report](docs/technical_report.md#71-methods). A series is
   flagged when more than 50% of its records arrived in the busiest 10% of report weeks; the flag
   uses only data available at the as-of week, and flagged nowcasts are shown as low confidence.

**Backtest.** Every 4 weeks from January 2023, the data are cut back to what had been reported by
that date (rebuilt from report dates), nowcasted, and compared with the count eventually reported.
The comparison method ("naive") takes the count reported so far at face value. CRPS is a proper
score that reduces to absolute error for a single-number estimate, so the two compare like for like.

**Results:** see [§7.3 of the technical report](docs/technical_report.md#73-results), generated by the pipeline. It
covers bias, CRPS and interval coverage by disease and horizon, the series with the largest
under-count, where the nowcast does not help, and the current picture. Backtest tables are in
`nowcast_backtest_summary.csv` and `nowcast_backtest_by_series.csv`; see also `nowcast_backtest.png`.

**Snapshots are a replay of reporting timing.** They are rebuilt from report dates in today's extract,
so later edits to records are not captured. The latest nowcast is in `data/processed/nowcast_latest.csv`
and `nowcast_latest.png`.

## Forecasting

`forecast.py` makes 1–4-week forecasts for the 10 forecast-eligible series. Every model returns a
full probability distribution over counts, so all of them are scored the same way and the 80% and
95% intervals come directly from those distributions.

| Model | Predictive distribution |
|---|---|
| Naive (benchmark) | Last week's count; uncertainty from how much counts changed over h weeks in the past 2 years (FluSight-style) |
| Rolling NB | Negative binomial around the mean of the last 8 weeks |
| Seasonal NB | Negative binomial around the same calendar weeks in up to 5 previous years |
| NB-AR | Count regression on recent levels plus seasonality, fitted separately for each horizon; ridge-penalised, and its mean is capped at twice the largest count seen so far (+5) |
| Ensemble | Equal-weight mixture of the four, fixed in advance |

**Evaluation** (`forecast_eval.py`):
- *Backtest on finalized data:* a forecast at every eligible week, using only data up to that week.
  Scores are CRPS, log score, absolute error and interval coverage. Relative CRPS compares each
  model with the naive benchmark; below 1 is better.
- *Choosing the model without peeking:* the primary model is the one that scores best on forecasts
  made before 2022, and its skill is then reported on 2022 onwards, which it never saw.
- *Real-time replay:* at past dates, recent weeks are replaced by what had actually been reported
  by then, used either as reported or corrected by the nowcast. This shows how much harder real-time
  forecasting is, and whether nowcasting helps.
- *Climate test:* NB-AR with the country's temperature and rainfall anomalies of the last 4 weeks
  (NOAA CPC; normals from 2003–2021) added as predictors, scored at the same origins as NB-AR
  (`forecast_climate_test.csv`). It is a test only: it is not in the ensemble or the model selection.

Results and the latest forecast table are in §8 of the technical report, which the pipeline
generates, and in `forecast_skill.png` and `forecast_latest.png`. They are not repeated here, so
that the README cannot fall out of step with them.

## Priority alerts

`priority.py` combines the current signals into one priority per country and disease for the latest
panel week, and lists the reasons. Each signal that fires adds one point; High = 2 or more,
Medium = 1, Low = 0.

| Signal | Fires when |
|---|---|
| National alarm | either detection method alarmed in the last 12 weeks |
| Province alarm | the subnational system alarmed in the same window |
| Reporting backlog | the nowcast expects at least 3 outbreaks in the last 4 weeks that are not yet reported |
| Rising forecast | the primary model's 4-week forecast is at least 1.5× the usual 4-week count (and at least 2) |
| HPAI in wild birds | wild-bird HPAI in the country in the last 26 weeks (HPAI only) |

The 12-week window is used because recent weeks are incomplete (see the real-time replay). Where
the nowcast flags batch reporting, the backlog and forecast signals are shown as notes only, and
confidence is low. Wild-bird HPAI comes from EMPRES-i records that the outbreak scope excludes
(`non-poultry bird`); mammals and captive animals are left out (`wild_bird_hpai_events.csv`).

This is a transparent decision aid, not a validated score: the rules were set in advance and not
tuned to WAHIS events. The current alerts and a partial check against recent WAHIS events are in
[§9 of the report](docs/technical_report.md#9-priority-alerts); the full table is
`outputs/tables/priority_alerts.csv`.
